# Changelog

Development milestones for the Deposplit project. Pre-release — entries are grouped by feature area rather than version number.

## Implemented

- **SSS libraries**: both the Kotlin (`Android/`) and Swift (`iOS/`) ports of Shamir's Secret Sharing are complete and fully tested.
- **Design**: the full app layer is designed — Web app/service protocol (4 message types + consent model), share holder onboarding, contact verification, identity recovery, contacts management, secret input methods, Ports & Adapters architecture. All documented in `CLAUDE.md`.
- **Android registration**: hexagonal boundary fully enforced for auth. `:hexagon/driving_ports/Identity` is the driving port, `:hexagon/driven_ports/IdentityStore` is the driven port, and `IdentityService` in `:hexagon/services/` owns all BouncyCastle crypto computation (Ed25519 + X25519 keypair generation, Ed25519 signing, X25519+HKDF-SHA-256+ChaCha20-Poly1305 encrypt/decrypt). `:app/auth/AndroidIdentityStore` implements `IdentityStore` using Android Keystore AES-256-GCM wrapping of private keys and `SharedPreferences` for storage; pseudonym and public keys stored plaintext. `DeposplitApp` wires `IdentityService(AndroidIdentityStore(this))` typed as `Identity`. BouncyCastle declared in `:hexagon/build.gradle.kts` (same rationale as the Web app/service hexagon). `SignInScreen` / `SignInViewModel` collect a pseudonym and call `register()`.
- **iOS app**: Full feature-parity implementation with Android. SwiftUI app targeting iOS 26+ with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`. All screens implemented: registration (`SignInView`), home with three tabs (Distributed/Held/Requests), contacts management with QR scan (`DataScannerViewController`) and manual entry, deposit flow (`Shamir.split` + `auth.encrypt` + `transport.depositShare`), recipient consent flows (approve/deny), sender-side reconstruction (`auth.decrypt` + `Shamir.combine`), QR display (CoreImage). Crypto via CryptoKit: X25519 key agreement + `hkdfDerivedSymmetricKey(using: SHA256.self, ...)` + `ChaChaPoly`. Ed25519 signing via `Curve25519.Signing.PrivateKey`. Private keys in Keychain (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`). API adapter uses `URLSession` + `SHA256.hash(data:)` for body hash. Uses `PBXFileSystemSynchronizedRootGroup` (Xcode 16+): no need to edit `project.pbxproj` when adding files.

All 87 tests pass (56 hexagon + 31 root). OpenAPI spec at `conf/openapi.yaml`.

- **Recipient-side signature verification + BYOR (self-hosted-instance backend)**: Two Ed25519 signatures now ride with every `ShareRequest` row, independent of the per-call transport-auth signature: `senderSignature` (set at `openShareRequest`, over `PayloadCanonical.forOpen`'s bytes — secretId/requestType/recipientKey/label/epochMillis(secretCreatedAt)/shareId/ciphertext) and `recipientSignature` (set at `respondToShareRequest`, over `PayloadCanonical.forRespond`'s bytes — requestId/approved-or-denied/ciphertext, required unconditionally including denials). `secretCreatedAt` is signed as epoch milliseconds and UUIDs are signed lowercase — both purely to keep the signed bytes byte-identical across the JVM, Kotlin, and Swift implementations (Swift's `UUID.uuidString` is uppercase by default, a real cross-platform footgun caught before it shipped). - **Holder-decrypts-at-pickup share-crypto redesign** (`deposplit.com/CLAUDE.md` "What is next" item 7): Replaced the encrypt-to-recipient *blind-courier* model — where a share stayed ciphertext bound to the sender's deposit-time keypair for its entire life, and so could never be reconstructed after the sender lost that keypair — with one where the holder decrypts at pickup and re-encrypts fresh at retrieve. **Pickup**: the holder now decrypts the deposited ciphertext with their own X25519 private key + the sender's X25519 public key (from their local contact record) and stores the resulting **plaintext** share — a single holder's `< k` share is information-theoretically empty on its own, so plaintext-at-rest (behind the OS's file-based encryption) is safe. **Retrieve**: the holder re-encrypts that stored plaintext to the *requester's current* X25519 public key, looked up live rather than pinned at deposit time — this is what makes k-of-n social recovery cryptographically possible at all, since no step depends on a keypair that might since have rotated or been lost. `reconstruct()` needed no code change on either platform, since its decrypt step already used the sender's own identity + the holder's *current* `xPublicKey`. `HeldShare.senderKey`/`ciphertext` → `contactId`/`senderPseudonym`/`plaintextShare`; `ShareMetadata.recipientKey` → `contactId` (both now a stable local UUID rather than a raw Ed25519 key, so the record survives a counterparty's key rotation); `ContactRepository` gained `getById` on all three hexagons. The **deposplit.com relay is entirely unchanged** — it still stores and forwards opaque ciphertext at both deposit and retrieve, blind at every phase; this is a client-only change to `hexagon`'s `ShareService`/`ShareRepository`/`ShareMetadataRepository` plus their local-storage adapters (`LocalShareRepository`/`LocalShareMetadataRepository` on Android and iOS). Applied to Android `:hexagon`/`:app`, iOS `hexagon`/`Deposplit`, and (for cross-platform *consistency*, not full parity — no denormalized pseudonym snapshot, since its held-shares view doesn't render a sender name yet) `deposplit.com/hexagons/phon` plus its `FileShareRepository`/`FileContactRepository`/`PhonyPhoneController`/`mySecrets.scala.html`.
